Design principle

The model proposes changes; deterministic code decides what is kept

Why not just let the agent run?

  • Grading is unforgiving. One broken test zeroes the case, and the deadline grades whatever is on disk. src/ must be valid at every moment.
  • The model's own report can't be trusted. It says "all three bugs fixed" while one is half-fixed.
  • The simulator is a free oracle. It's deterministic, takes about 0.4 s per seed, and checks invariants and expect blocks.

So the orchestrator owns:

  • the clock and the model budget
  • the last accepted copy of src/ (restored on any failure or SIGTERM)
  • the acceptance check: plain Python, never model judgement
  • the phases: when to review, verify, save and stop

What this buys

  • A bad edit costs a turn, not the case
  • Partial progress is kept: one of three bugs still counts
  • Behaviour is testable offline with a scripted model
  • Nothing is specific to one codebase: it uses only the contract every case shares (tests, sim, scenarios)

1 · Bootstrap (no model)

Public tests, a baseline sweep of every fault file over a sized set of seeds, then the cached context is built.

2 · Agent loop

Coverage first: every ticket item is mapped to a run that fails on the original code. Then the agent fixes and calls checkpoint() to get an edit accepted.

3 · First done()

Bounced back if there are unchecked edits. Otherwise a capped, item-by-item coverage review runs.

4 · Verification

A sweep on seeds 2000+ that were never seen. Failures send the agent back (at most 2 rounds), e.g. for a bug that was hidden behind the first.

5 · Near the deadline

The orchestrator saves unchecked edits itself, stops new turns, and runs a full or quick check, or reverts.

6 · Always

Finalize keeps a 20 s reserve. SIGTERM/SIGINT restore last_good/ before exiting.

Bootstrap: measure before the model speaks

About 40 s of plain Python that every later decision depends on
  • Adaptive sweep size. A short probe measures seconds per seed, then picks 5–15 extra seeds beyond the public ones so that one full sweep takes about 40 s on the machine at hand.
  • Baseline. The public scenario plus every fault file, recording which runs and seeds fail and which invariants they break. This is the reference for "no regression" and "progress".
  • Cached context (about 43K tokens): case docs, all of src/, the service and CURRENT platform docs from the corpus, the simulator's expect checker source, and the log event names seen in the evidence logs.
Seed count is sized from a measurement, not hard-coded: the grader's machine may be faster or slower than mine.

Coverage first: write_scenario

Some symptoms break no invariant, so no built-in run fails on them

The trap: fix the bugs that make runs fail, see everything green, stop. A symptom such as "tasks get re-queued for no reason" stays unfixed.

The rule (the first message to the agent): before editing, map every ticket item to a baseline run that fails because of it. If none exists, write a scenario whose expect block counts the symptom, until it fails on the original code.

  • The tool runs the new scenario on a pristine copy of the case and on the current code (5 seeds) and reports which fail.
  • A scenario the simulator can't run is BROKEN: excluded from checkpoints, never a "reproduction".
  • Valid agent scenarios join every later checkpoint, so a fix must make them pass too.
  • Fails on both the original and the current code → the open_bug flag is set: real work remains.

Making model calls reliable

The first full graded run scored 6/12, and every miss came from slow or stalled calls
  • Streamed calls with a hand-written SSE parser, so progress is visible byte by byte.
  • Idle timeout 60 s: no bytes at all → the call is stuck.
  • Stall timeout 60 s: keep-alive pings but no new content → also stuck (seen in real runs).
  • Thinking cutoff: still only thinking 75 s after the call started → abort and retry once with a nudge to think briefly and act.
    • The retry gets back the last 6,000 chars of the cut reasoning, so it doesn't redo the analysis. Retry times fell from 77–93 s to a median under 40 s.
  • Errors are local: a failed call pauses up to 10 s and retries; only 3 failures in a row end a phase. The proxy's 402 → BudgetExhausted.
  • Cost is tracked from the usage block in every response, with cache-aware pricing.
class ThinkingOverflow(LLMError):

    # thinking text so far

def overthink_nudge(partial):
    return (OVERTHINK_NUDGE +
      "<previous_reasoning>"

Coverage review, then verification

Only partly trusting the first done()

The first done() asks for one line per ticket item: item → kind → evidence.

liveness / correctness

Stuck, never finishes, wrong result, invariant broken. Evidence: a run that failed on the original code and passes now. It's fine if other bugs also made that run fail.

unwanted event

Re-queued, cancelled, retried, registered again. A run failing for other reasons does not count. Evidence: a scenario under the ticket's conditions whose expect counts that event (usually max 0), failing on the original code and passing now.

  • Capped at 6 turns or 150 s. It's a sanity pass, not a second investigation; otherwise it ate the time a verification sweep needed.
  • The cap is lifted when the agent's scenario fails on both the original and the current code (open_bug). There, the review found real work.
  • Hitting the cap → keep what's accepted, move on.

Verification: a sweep the size of a checkpoint on unseen seeds (2000+). Any failure goes back to the agent with examples ("possibly a bug hidden behind the one you fixed"), for up to 2 rounds.

Hidden grading uses 20 seeds per bug. Verifying on seeds the agent never saw is the closest local proxy for that.

Testing the fixer without a model

The control flow is deterministic, so it can be tested like ordinary code
  • ScriptedLLM replays a JSON script of tool calls through the real orchestrator. Each run is graded by the real grader.
  • test_llm_stream.py: stream parser, idle vs merely slow, pings-only stalls, thinking cutoff and the carry-over.
  • test_end_of_run.py: the quick check keeps a partial fix and rolls back bad edits.
  • claude_p_shim.py: a local stand-in upstream for the proxy, for end-to-end tests.
Every bug found in a real run (grep \|, broken scenarios counted as reproductions, a review that ran too long) became a script before it was fixed.

Case study: why B2 is hard

Three bugs in a GPU map-reduce service, one of them almost invisible

fixed reliably Bug 1

The worker drops finished tasks only if its report succeeds. After a network blip they stay listed in heartbeats forever, so the shard is never re-queued and the job is stuck in MAPPING.

Fails 10/10 under network.yaml.

the trap Bug 2

Spurious re-queues when heartbeats arrive reordered. It needs two fixes: the scheduler acks min(seen, hb_seq), and the worker must report the last heartbeat it sent.

Breaks no invariant: reorder.yaml fails 0/10 at baseline.

fixed reliably Bug 3

After gpu_submit_unknown and a NOT_FOUND reply, the client never resubmits, so the job is stuck in REDUCING under packet loss.

Fails 10/10 under lossy.yaml.

After fixing bug 1, bug 3 and only the scheduler half of bug 2, every built-in scenario passes. The shard_requeued counts don't change. Only a scenario that counts that event shows the half-fix.

The coverage-first rule and the "unwanted event" review exist for this pattern, and they're written generically: any symptom phrased as "X happens when it shouldn't".

What didn't work, and lessons

Measured, then kept or dropped

prototype, not shipped Per-seed counts in write_scenario

Judge a scenario by its own counting check and show event counts per seed on the original and current code ("5,4,8 before, 5,4,8 after"). Over 16 case runs it scored 33/36 against 53/54 for the submitted image, and ran slower. It caught the half-fix; the agent still ran out of time.

invalid measurement Grading at concurrency 6

Each container gets 2 CPUs; six on a laptop made the simulator 2× slower (0.73 vs 0.37 s per seed), and the results were meaningless. Benchmarks must match the real resources.

trade-off Thinking cutoff

Too low cuts good turns; too high lets a runaway turn eat a minute or more. 75 s plus carrying the reasoning into the retry was the best measured setting.

generality Don't overfit the practice simulator

The checker's failure wording is trusted only if the case's own check.py uses it, with a fallback otherwise. Rules are phrased by symptom kind, never by codebase.

kept Real runs find real tool bugs

grep \|, scenarios that only produce simulator errors, an uncapped review. Each one became an offline test first.

What I'd do next

Roughly in order of expected value on hidden cases

Systematic stress scenarios

Generate scenarios by varying fault parameters around the ticket, rather than relying on the agent's choices. Most B2 misses were about evidence, not code.

One agent per ticket item

Run them in parallel inside the 15 minutes, with merge handling for bugs that touch the same files.

Jev for cheap yes/no checks

"Does this patch disable functionality?" or "Is this limit set from the fixed code?" at almost no cost, to reduce the risk from private regression tests.

On-demand corpus retrieval

For services whose docs are too large to include in the cached context.

Smarter thinking control

Cut runaway thinking earlier without losing good long turns; each cut still costs about 75 s.

Forgive common scenario mistakes

Accept a base: key inside the YAML or a scenarios/ prefix on fault paths instead of rejecting them: one turn saved per case.

Takeaways

  • A deterministic oracle plus a snapshot make model mistakes cheap: a bad edit costs a turn, not the case.
  • Most early points were lost to plumbing (stalled streams, runaway thinking, unsaved progress), not reasoning. Fix those first.
  • The hardest remaining failure is evidence quality for symptoms that break no invariant. Tools can surface it; the model still has to act on it.
  • Every change was measured under the real grading setup and dropped if it didn't help.
